# contracts/ — the model and every shared contract

The schema the code is generated from or reads at run time, and the registry it is driven by, which lives with the
data in `data/registry/`; what each rule means: `docs/DATA_ARCHITECTURE.md`. A change to either is
validated by `python3 -m radar model validate --json` and, when a generated file depends on it, regenerated by
`python3 -m radar model generate` in the same commit (pre-commit runs both, with `--check`). `model generate` also lays
out every JSON file here and in the registry: a value on one line when it fits in 120 columns or holds no object or
array.

## Map

- `model/`: `entities.json` (every entity kind), `views.json` (the public read model's views), `tools.json` (the MCP
  tools), `value_types.json` and `registry_types.json`.
- `data/registry/` (`MVR_DATA` points at another data folder, a fixture's): `categories.json`, `category_profiles/<category id, dots as underscores>.json`,
  `spec_definitions.json`, `spec_groups.json`, `units.json`, `dimensions.json`, `vocabularies/<vocabulary>.json`,
  `ai.json` (each AI use's model and caps), `search.json` (the embedding model and the ranking knobs), `feed.json`
  (the news desk's rules).
- `operations.json` (every operation: CLI command, `--json` shape, admin screen, MCP tool), `logging.json` (both
  loggers' fields and redaction), and `languages.json`. The words the radar never
  writes (`no_filler.json`) and the agents' prompts (`prompts/<use>.md`, one file a use, the live prompt; no older
  version is kept) are data, in `../data/`.
- `firebase/`: the store's access rules (`firestore.rules`, `storage.rules`: default deny, public reads only) and its
  composite indexes (`firestore.indexes.json`), which `firebase.json` names.

## Generated files

Never hand-edited (AGENTS.md rule 8); `test_layout` lists them as `GENERATED`.

| input | output | command |
|---|---|---|
| `model/entities.json` | `radar/domain/model/entities.py` | `radar model generate` |
| `model/views.json` | `app/src/domain/views.ts`, `app/src/adapters/generated-views-zod.ts` | `radar model generate` |
| `model/tools.json` | `radar/adapters/web/mcp_tools.json` | `radar model generate` |
| the store's read model | `llms.txt`, `llms-full.txt` (gitignored, in `dist/` or the build) | `radar site export` |
| `app/package.json` | `app/package-lock.json` | `npm install` in `app/` |

## Recipes

Every label and description is `{<code>: text}` in every language of `languages.json`. A new id is never quoted in
code (`test_data_driven`); code reads it from the registry.

- **A spec:** an entry in `spec_definitions.json` (id, datatype, unit or vocabulary, label, description); its place in
  each category profile that shows it (`sections`, `groups`, `facets`). `model validate`, then the
  `quality coverage --category <id>` command shows it.
- **A category:** an entry in `categories.json` (id, label, domain, pipeline, glyph, description) and its profile in
  `category_profiles/`; the site's pages and hubs follow from the registry.
- **A term:** an entry in its `vocabularies/<vocabulary>.json` (id, label); what it means is its marks (as `occurred`
  or `sets_status`), never a branch in code.
- **A language:** an entry in `languages.json`, a folder `app/src/shell/i18n/messages/<code>/` with every key of the
  default language, and that language in every label of the registry (`i18n-keys.test.ts`,
  `test_third_language_added_to_contract_needs_no_code_change`).
- **A prompt change:** edit `data/prompts/<use>.md`, keeping its inputs and output schema
  (`test_prompts`); run its eval (`radar eval run <use>`; on the project it spends, `docs/CLI.md`).
